    RUST(1)                     Occupant's Manual                    RUST(1)

NAME
     rust — a language that will not let you do the thing

SYNOPSIS
     rust [--fight-with] borrow-checker [--for] three hours
          [--then] concede it was right

DESCRIPTION
     Most languages trust you and inform you afterwards. Rust declines to
     trust you and informs you in advance. The compiler is not a linter
     with opinions; it is a proof obligation with a bad attitude, and the
     program does not exist until the obligation is discharged.

     Three rules do nearly all of the work:

     1.  Every value has exactly one owner. Assign a non-Copy
         value elsewhere and ownership moves: the old name is not
         stale, it is gone, and saying it is a compile error rather than a
         Tuesday. Types that are Copy — integers, bools, shared
         references — are duplicated instead, and the original stays
         perfectly usable. Forgetting that exception is how the rule gets
         mis-taught.

     2.  You may hand out any number of shared references, or exactly
         one mutable reference, and never both at once. Every data race
         you have ever debugged is a violation of that one sentence.

     3.  A reference may not outlive the thing it refers to. Lifetimes
         are how you say so out loud when the compiler cannot work it
         out alone:

             fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
                 if a.len() >= b.len() { a } else { b }
             }

         which reads: whatever I hand back is good for as long as
         both of the things you handed me are.

DIAGNOSTICS
     error[E0502]: cannot borrow `x` as mutable because it is also
                   borrowed as immutable

     You will resent this message. You will then discover that the code
     it refused to compile was, in fact, wrong.

BUGS
     The learning curve is real and the evangelism is insufferable. Both
     of those are true and neither is an argument.

SEE ALSO
     ownership(7), lifetimes(7), a long walk(1)
    The thing nobody says out loud: the appeal is not speed. It is that the compiler makes you state an invariant you were already relying on and had never written down.

    Opinion 001

    Dashboards are better
    with JavaScript animation.

    Nobody asked. Filed anyway.

    The standard objection to animated dashboards is that motion is decoration, and decoration on a serious instrument is a tell. I agree with the objection entirely. I reject the conclusion, because it is an argument against bad animation that has been mistaken for an argument against animation.

    Here is the distinction that resolves it, and it fits on one line: animate the data, not the chrome.

    A bar that slides up because the page finished loading is decoration. It encodes nothing the final frame did not already say, it costs the reader time, and it is the reason the objection exists. Delete it. But a bar that moves from its old height to its new height when the filter changes is not decoration. It is the only encoding of change anywhere on the screen. Take the motion away and you have two pictures, and the reader has to do the diffing themselves, from memory, badly.

    The technical name for what the motion buys you is object constancy: the mark stays the same object across the change, so the reader tracks it instead of re-reading the chart. That is the whole mechanism. It is why a transition between two states of the same chart earns its keep and an entrance animation never does.

    So the rule I actually work to is narrow. Motion is permitted when it carries a change in the data and forbidden when it does not. A filter change, a re-sort, a drill-down, a new value arriving on a live series — those are transitions, and they should be animated. A page load is not a change in the data. It is the beginning of the data. Draw it and get out of the way.

    The exhibit to the right is the argument. Change the range on both charts and watch which one you can read.

    ↓ the paper that supports me

    Heer & Robertson, Animated Transitions in Statistical Data Graphics, IEEE InfoVis 2007. Animated transitions between chart states measurably improved subjects’ ability to track values.

    ↓ the paper that complicates it

    Tversky, Morrison & Bétrancourt, Animation: can it facilitate?, IJHCS 2002. A careful review finding that a great many claimed benefits of animation vanish once the static condition is given the same information. In fairness it is aimed at animation broadly rather than at transitions between two states of one chart, which is the narrow thing argued here — so it complicates my case rather than refuting it. Read it before taking my side.

    This opinion is worth exactly what you paid for it. Three concessions, freely given:

    1. Motion you cannot interrupt is a cage. Every transition here takes the next instruction immediately.
    2. I keep transitions under about 400 ms, past which they start reading to me as a wait rather than as motion. That is a working preference and not a result — the literature reports timings that depend on the task, and Heer & Robertson tested considerably slower ones. These run at 380.
    3. If the reader has asked their operating system for less motion, the argument is void and you honour the request without negotiating.
